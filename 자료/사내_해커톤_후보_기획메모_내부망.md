# 사내 해커톤 후보 기획 메모 — 내부망 활용형

> 용도: 외부망 활용형 후보 논의 완료 후 최종 계획서(Word) 작성 시 컨텍스트 복원용.
> 현재 단계에서는 팀 구성/인원/세부 구현방식이 미정이므로, 확정사항과 논의 포인트를 중심으로 기록.
> 해커톤 주제: AI를 활용한 사내 업무 개선 및 효율화.

---

## 0. 공통 전제

### 일정/환경
- 총 3회 진행, 회차별 4시간.
- 1회차: GitHub Copilot 교육, 팀 구성, 주제 선정.
- 1회차~2회차 사이 9일(주말 2일 포함): 사실상 핵심 개발 기간.
- 2회차: 팀별 개발(스프린트 2회), 1차 산출물 제출, 팀별 결과 발표.
- 2회차~3회차 사이 3일(주말 2일 포함): 대규모 개발보다는 수정·보완 기간으로 보는 것이 현실적.
- 3회차: 최종 발표.
- 본업 병행. 별도 업무시간 확보 수준 불명. 팀 구성/인원/개발역량도 1회차에 결정.
- 따라서 복잡한 DB/인증/협업/대규모 아키텍처는 지양. 기능 일부가 실패해도 MVP가 남는 구조 선호.

### 개발 제약
- 사내정보는 코드/데이터/프롬프트 등 어떤 형태로도 외부 개발에 사용 불가.
- 개발 시 공개데이터 또는 가상데이터만 사용.
- 내부망 활용형은 외부에서 개발 후 프로그램을 내부망에 반입하여 실제 사내 데이터에 적용하는 방식.
- 사내에는 PTU 방식 GPT-5.4 mini가 있음.
- 외부 개발 단계에서는 유사 역할의 외부 LLM으로 AI 기능/프롬프트를 설계·검증.
- 실제 내부망 활용이 결정되면 해당 팀에서 사내 GPT-5.4 mini 연동.
- GitHub Copilot 제공. Copilot 내에서 다양한 모델 선택 가능.
- 별도 GPT/Gemini API 사용권 제공은 확인되지 않음.

### AI/API 개발 전략
- 최종 설계상 LLM 호출부는 독립 모듈로 분리.
- 개발 중 반복 API 호출은 최소화.
- 프롬프트/입출력 규격은 웹 기반 LLM에서 직접 검증 가능.
- 검증 결과(JSON 등)를 mock 응답으로 저장해 Python/UI 개발에 활용.
- 필요 시 마지막 통합 단계에서만 실제 API를 소량 호출하여 end-to-end 정상 작동 확인.
- 내부망 반입 시 외부 LLM 연결부를 사내 GPT-5.4 mini 연결부로 교체할 수 있는 구조 지향.
- 1회차 직후 입력/출력 데이터 형식을 먼저 확정해 팀원별 병렬 개발이 가능하도록 하는 것이 중요.

# 후보 1. AI RFP 작성 지원 도구

## 1. 문제/목적

회사는 수행사보다 발주사 역할을 많이 하는 편.

발주 초기의 요구사항은 완성된 명세가 아니라 아이디어/메모 수준으로 존재하는 경우가 많음.

예:
- 관리자 화면 필요
- 조회가 편해야 함
- 기존 시스템과 연동
- 사용자별 권한 필요
- 통계도 볼 수 있으면 좋겠음

이를 실제 RFP에 넣기 위해서는:
1. 요구사항을 구체화
2. 모호하거나 누락된 부분 확인
3. 유사 요구사항 통합
4. 기능/비기능 등 분류
5. 수행사가 범위·설계·개발을 판단할 수 있는 표현으로 재작성
6. 요구사항 명세화
7. 최종 RFP 형식으로 구성

하는 작업이 필요.

목표는 단순한 `메모 → RFP 자동작성`이 아니라 **요구사항 구체화 → 검토 → 명세화 → RFP 초안 생성**을 지원하는 것.

## 2. 기본 프로세스

```text
[아이디어 / 요구사항 입력]
        ↓
[AI 요구사항 분석]
        ↓
- 모호한 표현 탐지
- 누락 가능 항목 탐지
- 유사 요구사항 통합
- 기능/비기능 요구사항 분류
        ↓
[발주·수행 관점 요구사항 구체화]
        ↓
[사용자 검토 / 수정 / 승인]
        ↓
[요구사항 명세 생성]
        ↓
[RFP 초안 생성]
```

AI가 처음부터 RFP 전체를 바로 생성하는 방식은 지양.

## 3. AI 역할

예시 입력:

> 관리자 화면에서 사용현황을 보고 싶다.  
> 엑셀로도 받을 수 있어야 한다.  
> 사용자마다 권한이 달라야 한다.

예상 변환:

| ID | 구분 | 내용 |
|---|---|---|
| REQ-001 | 기능 | 관리자는 지정한 기간의 서비스 이용현황을 조회할 수 있어야 함 |
| REQ-002 | 기능 | 조회 결과를 Excel 파일로 다운로드할 수 있어야 함 |
| REQ-003 | 기능 | 사용자 권한에 따라 접근 가능한 기능 및 메뉴를 제한할 수 있어야 함 |
| REQ-004 | 확인 필요 | 이용현황에 포함할 지표 정의 필요 |
| REQ-005 | 확인 필요 | 권한의 종류와 권한별 접근 범위 정의 필요 |

핵심 원칙:
- 불명확한 내용을 AI가 임의로 확정하지 않음.
- 추가 결정이 필요한 사항은 `확인 필요`로 분리.
- 단순 윤문보다 **“이 요구사항만으로 수행사가 범위·견적·설계·개발을 판단할 수 있는가?”** 관점에서 검토.

예:
> 빠른 응답속도를 제공해야 한다.

→ 대상 화면/기능, 측정 기준, 목표 응답시간 등 객관적인 검증 기준이 필요하다고 제안.

예:
> 기존 시스템과 연동한다.

→ 연동 대상, 방식(API/DB/File 등), 데이터 범위, 호출 방향, 주기 등 추가 정의 필요사항 제안.

## 4. RFP 생성

사용자가 검토·확정한 요구사항을 기준으로 RFP 초안 생성.

예상 구성(세부 양식은 팀 논의 후 확정):
- 사업 개요
- 추진 목적
- 사업 범위
- 요구사항
  - 기능 요구사항
  - 비기능 요구사항
  - 인터페이스 요구사항
  - 보안 요구사항
- 수행 및 관리 요건
- 산출물
- 기타 사항

## 5. 해커톤 MVP

```text
자유로운 요구사항 입력
↓
AI 요구사항 분석·구체화
↓
요구사항 명세표 생성
↓
사용자 검토·수정
↓
RFP 초안 생성
↓
Markdown 또는 DOCX 출력
```

해커톤 범위에서 제외/후순위:
- 로그인
- DB 기반 프로젝트 관리
- 협업
- 버전 관리
- 복잡한 결재/워크플로

## 6. 개발 데이터

실제 사내 프로젝트 정보 사용 금지.

가상의 프로젝트와 가상 요구사항으로 개발.

예:
- 가상의 사내 교육관리 시스템 구축
- 초기 요구사항 10~20개를 일부러 아이디어/메모 수준으로 생성
- Before: 모호한 요구사항
- After: 명세화된 요구사항 + 확인 필요사항 + RFP 초안

## 7. 개발/운영 구조

개발:
```text
가상 요구사항
↓
Python/UI
↓
외부 LLM으로 프롬프트 및 AI 출력 검증
↓
mock 응답 기반 개발
↓
필요 시 최종 API 연결 테스트
```

실제 사내 활용:
```text
사내 요구사항
↓
내부망 프로그램
↓
사내 GPT-5.4 mini
↓
요구사항 명세 + RFP 초안
```

## 8. 강점/리스크

강점:
- 발주 업무와 직접 연결.
- AI의 역할이 명확함.
- 가상 데이터 제작이 쉬움.
- Before/After 데모 효과가 큼.
- 구조화/분류/재작성 중심이라 mini 모델에도 비교적 적합.
- Python 구현 난이도 상대적으로 낮음.

주의:
- 단순 `GPT에 RFP 써줘` 수준으로 보이지 않도록 중간 분석·검토 단계가 핵심.
- RFP 구성/요구사항 분류 체계는 주제 선정 후 팀원들과 구체화 필요.
- AI가 없는 요구사항을 사실처럼 만들어내지 않도록 `확인 필요` 처리 중요.

# 후보 2. AI 문서 전처리·구조화 도구

## 1. 문제/목적

PDF, DOCX, PPTX 등 일반 업무문서는 사람이 읽기 좋게 만들어져 있어 AI/RAG 입력 데이터로 바로 활용할 때 구조 손실이 발생할 수 있음.

대표 문제:
- PDF의 불필요한 줄바꿈
- 페이지 전환으로 문장 분리
- 제목/소제목/본문 계층구조 손실
- 페이지 번호/머리글/바닥글 혼입
- 표 구조 손실
- 이미지와 본문 위치 관계 손실
- PPTX 텍스트 읽기 순서 혼선

목표:
**원문 내용을 최대한 보존하면서 사람이 보는 문서를 AI가 활용하기 쉬운 Markdown 형태로 자동 전처리·구조화.**

단순 파일 변환보다 `AI/RAG용 데이터 준비`가 목적.

## 2. 핵심 원칙

- 원문 보존 최우선.
- 요약하지 않음.
- 번역하지 않음.
- 내용을 임의로 재작성하지 않음.
- AI는 새로운 내용을 생성하기보다 문서의 원래 구조/관계를 판단·복원하는 역할.
- 변환을 신뢰하기 어려운 경우 AI가 추정해 확정하지 않고 사용자 확인 대상으로 표시.

## 3. 기본 프로세스

```text
[PDF / DOCX / PPTX 업로드]
        ↓
[Python 기본 추출]
- 텍스트
- 제목 후보
- 표
- 이미지
- 페이지/슬라이드 정보
        ↓
[기본 전처리]
- 불필요한 줄바꿈 제거
- 페이지 번호/머리글/바닥글 제거
- 단어 중간 분리 복원
- 기본 표 구조 분석
        ↓
[AI 구조 분석]
- 제목 / 소제목 / 본문 구분
- 문단 관계 판단
- 잘못 분리된 내용 복원
- 문서 계층구조 정리
        ↓
[필요 시 사용자 확인]
        ↓
[Markdown 생성]
```

기계적 처리는 Python 우선.
규칙만으로 판단하기 어려운 구조를 AI가 보완.

## 4. 표 처리

가장 큰 기술 리스크 중 하나.
모든 표를 무조건 Markdown Table로 만드는 것을 목표로 하지 않음.

### A. 단순 표
일반 행×열 구조 → Markdown Table.

예:
```markdown
| 구분 | 2025 | 2026 |
|---|---:|---:|
| 매출 | 100 | 120 |
| 비용 | 80 | 90 |
```

### B. 병합이 있으나 관계 해석 가능
표의 외형보다 의미 관계를 보존하는 **구조화 텍스트**로 평탄화.

예: `국내/해외`가 세로 병합된 표

```markdown
### 국내
- 주식
  - 2025: 100
  - 2026: 120
- 채권
  - 2025: 50
  - 2026: 70

### 해외
- 주식
  - 2025: 30
  - 2026: 60
- 채권
  - 2025: 20
  - 2026: 40
```

### C. 복잡한 다중 병합
가로 병합 + 세로 병합 + 다단 헤더 등이 복합적으로 존재.

처리 방향:
```text
원본 셀 정보
+ 병합 범위
+ 행/열 위치
↓
AI 구조 해석 시도
↓
신뢰 가능 → 구조화 텍스트
불명확 → 원본 위치 + Warning
```

예:
> 표 구조 확인 필요  
> 복합 병합으로 인해 일부 셀의 상하위 관계를 명확하게 판단하기 어렵습니다.  
> 원본: Page 14

성공 기준:
- 모든 표 완벽 변환 X
- 단순 표는 Markdown 변환
- 복잡한 표는 정보 손실을 최소화한 구조화 텍스트
- 신뢰하기 어려우면 원본 위치와 함께 사용자 확인 표시

## 5. 이미지 처리

문서 내 이미지는 별도 이미지 파일로 추출.
Markdown에서 원래 위치에 참조 유지.

예:
```markdown
![이미지](images/image-003.png)
```

해커톤 MVP에서는 이미지 내용 자동 분석/설명은 필수 아님.

이미지가 존재하면:
- 어떤 이미지 파일이 생성됐는지
- 원본 문서 어디에 있던 이미지인지
- Markdown의 어느 위치와 연결되는지

확인 가능해야 함.

## 6. Conversion Report

선택적으로 변환 리포트 생성.

목적:
- 문서 구조/변환 결과 확인
- 변환 실패 또는 불확실 영역 확인
- 원본에서 재확인해야 할 위치 제공
- 이미지가 있는 경우 이미지-원문-Markdown 위치 관계 확인

예시:

```text
Conversion Report

원본: example.pdf
페이지: 37

변환 결과
- 제목/소제목: 15개
- 표: 8개
  - Markdown 변환: 5
  - 구조화 텍스트: 2
  - 확인 필요: 1
- 이미지: 4개

확인 필요
- Page 12: 복합 병합 표
- Page 27: 문단 순서 확인 권장

이미지
- image-001.png / 원본 Page 4 / 2. 사업 개요
- image-002.png / 원본 Page 13 / 4. 추진 계획
```

사용자용 리포트는 JSON보다 `conversion_report.md` 선호.
필요 시 내부 메타데이터는 JSON으로 별도 관리 가능.

## 7. Report UI 설정

예:
```text
☐ 변환 리포트 생성
```

- 기본값 OFF.
- 사용자가 체크하면 이후에도 ON 상태 유지.
- 해제하면 이후에도 OFF 상태 유지.
- 브라우저 localStorage 등으로 설정 상태 보존 가능.
- 단, 설정 영구 저장 구현은 해커톤 MVP에서 후순위 가능.

이미지가 포함된 문서:
- Conversion Report 필수.
- UI에서 자동 ON + 해제 불가 방식 고려.
- 이유: 이미지 파일과 원본/Markdown 위치 관계 확인 필요.

## 8. 출력 규칙

불필요하게 모든 결과를 ZIP으로 만들지 않음.

| 상황 | MD | ZIP | Report |
|---|:---:|:---:|:---:|
| 이미지 없음 + Report OFF | O | - | - |
| 이미지 없음 + Report ON | O | 선택 | O |
| 이미지 있음 | O | O | 필수 |

### 이미지 없는 일반 문서
기본 결과:
- `document.md`

Report ON:
- `document.md`
- `conversion_report.md`
- 필요 시 묶음 ZIP도 선택 가능

### 이미지 있는 문서
Markdown은 별도로 바로 다운로드 가능하게 제공.
전체 파일은 ZIP 제공.

```text
converted_document.zip
├─ document.md
├─ images/
│  ├─ image-001.png
│  ├─ image-002.png
│  └─ image-003.png
└─ conversion_report.md
```

결과물만 필요한 사용자가 매번 ZIP을 풀지 않도록 `document.md` 직접 다운로드를 항상 우선 고려.

## 9. 해커톤 MVP/확장 순서

처음부터 PDF/DOCX/PPTX 모두 지원하지 않음.

### 1차 MVP
```text
PDF
↓
텍스트 / 표 / 이미지 추출
↓
Python 전처리
↓
AI 구조 분석
↓
Markdown
↓
다운로드
```

### 이후 확장
1. DOCX 지원
2. PPTX 지원
3. 복잡한 표 처리 개선
4. Conversion Report 개선
5. 이미지 처리 고도화
6. 필요 시 AI/RAG용 청킹·메타데이터 기능 검토

PPTX는 레이아웃/읽기 순서 문제가 있어 후순위.

## 10. 개발 테스트 데이터

사내 문서 사용 금지.

정부기관/SEC/공공기관 등 공개 문서 활용.

서로 다른 유형을 테스트:
- 텍스트 중심 문서
- 표가 많은 문서
- 이미지 포함 문서
- 복잡한 레이아웃 문서

데모 시 가능하면:
1. 원본 PDF
2. 일반 텍스트 추출 결과
3. AI 전처리·구조화 Markdown

비교하여 효과를 시각적으로 보여줌.

## 11. 개발/운영 구조

개발:
```text
공개 문서
↓
Python 파싱/전처리
↓
외부 LLM으로 구조 분석 프롬프트 검증
↓
mock 응답 활용
↓
필요 시 마지막 API 연결 테스트
↓
Markdown
```

실제 사내 활용:
```text
사내 문서
↓
Python 파싱/전처리
↓
사내 GPT-5.4 mini
↓
Markdown
↓
사내 AI / RAG / 지식문서 등에 활용
```

외부/내부 LLM 연결부는 교체 가능하게 분리.

## 12. 강점/리스크

강점:
- 실제 사내 AI 활용 과정의 문서 전처리 문제와 직접 연결.
- 결과물 활용처가 명확함.
- Python 비중이 높아 GitHub Copilot 활용 효과를 보여주기 좋음.
- AI가 필요한 부분과 규칙 기반 처리를 분리 가능.
- 공개 문서만으로 충분히 개발/시연 가능.

리스크:
- RFP 도구보다 구현 난도가 높음.
- 특히 병합 표/복잡한 PDF 레이아웃이 핵심 기술 리스크.
- 완벽 변환을 목표로 하면 일정 내 실패 가능성이 높으므로 Warning/사용자 확인 구조가 필수.
- 파일 형식 지원 범위를 단계적으로 제한해야 함.
